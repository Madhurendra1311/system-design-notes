# WhatsApp System Design: Chat Messaging Interview Prep

Based on the walkthrough description you shared. The description names the features and non-functional requirements below, but not the exact design choices. Check those against the video.

---

## 1. Problem Statement

Design a chat messaging system that supports:

1. One-to-one messaging
2. Read receipts (sent, delivered, read)
3. Group messaging
4. Last seen visibility, with privacy controls
5. Image sharing

---

## 2. Clarifying Requirements

**Functional**
- Send and receive text messages in real time
- Show delivery and read status for each message
- Create and message groups
- Show a user's last seen time, subject to privacy settings
- Send and receive images

**Non-functional**
- **Message ordering:** messages in a conversation appear in the order they were sent
- **Reliability:** no message is lost, even if the network or a server fails
- **Retries:** failed deliveries are retried safely
- **Idempotency:** a retried send does not create duplicate messages
- **Low latency:** delivery in well under a second when both users are online
- **Scalability:** hundreds of millions of users and billions of messages per day
- **Load balancing:** connections and requests spread across servers
- **Availability:** prefer availability over strict consistency for presence data

**Scale assumptions to state**
- 500 million daily active users
- 40 messages per user per day, so about 20 billion messages per day
- Average load around 230,000 messages per second, with peaks several times higher
- Average message size around 100 bytes for text. Images are much larger and stored separately.

Doing this math out loud is a strong signal in interviews. It justifies the design choices later.

---

## 3. High-Level Architecture

| Component | Responsibility |
|---|---|
| Client app | Sends messages, sends acknowledgments, maintains a persistent connection |
| Load balancer | Distributes connections across gateway servers |
| Chat gateway (connection servers) | Holds persistent WebSocket connections, one per online user |
| Session service | Maps user_id to the gateway server holding that user's connection |
| Message service | Validates, assigns sequence numbers, stores, and routes messages |
| Message store | Durable storage of messages, partitioned by conversation |
| Group service | Group membership and group metadata |
| Presence service | Tracks online status and last seen times |
| Media service | Handles image uploads and downloads through object storage and a CDN |
| Push notification service | Notifies offline users through APNs and FCM |
| Message queue | Decouples message routing, delivery, and notifications |

---

## 4. Data Model

**Message**
- message_id (UUID, generated by the client, used for idempotency)
- conversation_id
- sender_id
- sequence_number (per conversation, used for ordering)
- content or media_url
- created_at
- status (sent, delivered, read) tracked per recipient

**Conversation / Group**
- conversation_id
- type (one-to-one or group)
- member list
- created_at

**Inbox (per user)**
- user_id
- conversation_id
- last_message_seq
- unread_count

Storage choice: a wide-column store such as Cassandra or HBase works well. Partition by conversation_id and cluster by sequence_number. This keeps a conversation's messages together and makes "fetch the latest 50 messages" a single range read.

---

## 5. Sending a Message

1. The sender's client creates a message with a client-generated message_id and sends it over its WebSocket connection.
2. The chat gateway passes it to the message service.
3. The message service checks whether message_id already exists. If so, it returns the stored result. This is the idempotency check.
4. The message service assigns the next sequence_number for the conversation and writes the message to the store.
5. The server acknowledges the sender ("sent" status, one tick).
6. The message service looks up each recipient's gateway through the session service and pushes the message.
7. When the recipient's client receives it, the client sends a "delivered" acknowledgment, and the sender sees two ticks.
8. When the recipient opens the conversation, the client sends a "read" acknowledgment, and the sender sees blue ticks.
9. If a recipient is offline, the message stays in the store and a push notification is sent.

---

## 6. Message Ordering

- Ordering is guaranteed **within a conversation**, not across all messages in the system. That is enough for users and much cheaper to achieve.
- The message service assigns a monotonically increasing sequence number per conversation. Because one partition owns each conversation, ordering is simple to enforce.
- Clients sort by sequence number. If a client sees a gap (for example, sequence 42 arrives before 41), it requests the missing messages.

Interview point: global ordering across all chats would require a single bottleneck. Per-conversation ordering scales because conversations are independent.

---

## 7. Retries and Idempotency

- **Client retries:** if no acknowledgment arrives within a timeout, the client resends with the same message_id.
- **Server dedupe:** the message service checks message_id before writing. A duplicate returns the existing message instead of creating a new one.
- **Exponential backoff with jitter** prevents retry storms when a service recovers.
- **Delivery retries:** the queue retries failed pushes. Undelivered messages remain in the store, so a reconnecting client fetches what it missed.

Key idea: the client, not the server, generates the message_id. That way a retry after a timeout always refers to the same message.

---

## 8. Read Receipts

- Each delivery and read event is an acknowledgment message with the message_id and the recipient's id.
- Group messages need per-member status. Store the list of members who have read a message, or track a read cursor per member, which is cheaper: "this member has read up to sequence 87."
- Read receipts can be turned off by the user. The server respects that setting when deciding whether to send the "read" event.

---

## 9. Group Messaging

**Fan-out approaches**
- **Fan-out on write:** store one copy of the message per member's inbox. Reads are fast, but a large group multiplies writes.
- **Fan-out on read:** store the message once in the conversation and let members read from it. Cheaper writes, but more work at read time.

**Practical approach**
- Small groups (WhatsApp limits groups to a few hundred members in older versions, and more in newer ones): fan-out on write to each member's gateway.
- Large or broadcast-style groups: store once and fan-out on read or use batched delivery.

Group membership changes (join, leave, admin changes) are written to the group service and emitted as events, so all members see the change in order.

---

## 10. Last Seen and Presence

- Clients send a heartbeat every few seconds while connected. The presence service records the last heartbeat time.
- **Last seen** is the most recent time the user was active. Writes are frequent, so use an in-memory store like Redis with a TTL.
- **Privacy settings:** the server checks the viewer's permission before returning last seen. Options include everyone, contacts only, or nobody.
- Presence is eventually consistent and approximate. A few seconds of delay is acceptable.
- Avoid broadcasting every presence change to every contact. Instead, subscribe clients only to presence for people they are actively chatting with.

---

## 11. Image Sharing

1. The client asks the media service for an upload URL (a pre-signed URL to object storage).
2. The client uploads the encrypted or raw image directly to object storage. The chat server never handles the bytes.
3. The client sends a chat message containing the media_url, thumbnail, and metadata.
4. Recipients download the image through the CDN.
5. Background workers generate thumbnails and compressed versions.

Keeping large files out of the message path protects latency and keeps chat servers lightweight.

---

## 12. Connection Management and Load Balancing

- Each user keeps one persistent WebSocket connection to a gateway server.
- The session service maps user_id to gateway_id. This is updated on connect and disconnect.
- Gateways are stateless with respect to message history, so they can be added or removed easily.
- If a gateway crashes, clients reconnect through the load balancer and the session map is refreshed.
- Connection count is the main scaling limit. Use many gateways, each holding a few hundred thousand connections.

---

## 13. Likely Follow-Up Questions

**Q: How do you guarantee a message isn't lost?**
A: Write to durable storage before acknowledging the sender. Replicate the store. Clients resync missed messages by sequence number after reconnecting.

**Q: How do you prevent duplicate messages?**
A: The client assigns a unique message_id. The server checks for it before writing, so retries are safe.

**Q: Why is ordering per conversation and not global?**
A: Global ordering needs a single sequencer and would not scale. Users only care about order within a chat.

**Q: What happens if the recipient is offline?**
A: The message is stored, a push notification is sent, and the client fetches missing messages when it reconnects.

**Q: How do you scale a group with 1,000 members?**
A: Fan-out on read, or batched delivery to member gateways. Store the message once and let members pull it.

**Q: How do you show "last seen" without overloading the system?**
A: Heartbeats into an in-memory store with TTL. Only subscribe clients to presence for active conversations and respect privacy settings server-side.

**Q: How do you handle images?**
A: Pre-signed upload to object storage, CDN delivery, and only a reference in the message.

**Q: Where does end-to-end encryption fit?**
A: The server only sees ciphertext. Keys are exchanged between clients. This affects search and server-side features, so mention the trade-off.

**Q: How would you handle a server failure in the middle of sending?**
A: The client times out and retries with the same message_id. The idempotency check makes it safe.

---

## 14. Trade-offs to Discuss

| Decision | Benefit | Cost |
|---|---|---|
| Per-conversation ordering | Scales well, simple to enforce | No global ordering |
| Client-generated message_id | Safe retries | Client must be trusted to generate unique IDs |
| Fan-out on write for groups | Fast reads | Expensive for very large groups |
| Fan-out on read for large groups | Cheap writes | Slower reads |
| Heartbeat presence in Redis | Fast, low overhead | Approximate, eventually consistent |
| Images via pre-signed upload | Keeps chat servers light | Two-step send process |
| Persistent WebSockets | Real-time delivery | Connection servers consume memory and need careful scaling |

## 16. One-Minute Summary

A chat system keeps a persistent WebSocket connection for each online user, served by gateway servers behind a load balancer. A session service maps users to gateways. The message service assigns per-conversation sequence numbers, uses client-generated message IDs for idempotency, and stores messages in a partitioned wide-column store. Delivery and read receipts are acknowledgment events. Groups use fan-out on write for small groups and fan-out on read for large ones. Presence uses heartbeats in an in-memory store with privacy checks. Images go directly to object storage through pre-signed URLs and are served through a CDN.
